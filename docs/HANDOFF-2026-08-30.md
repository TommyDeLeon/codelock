## The bug that mattered

The lock could not be solved out of. It is fixed; the shape is worth knowing
because three separate defects stacked into one symptom.

The shell took the screen and loaded the lock page, but the **server session
stayed `ARMED`** — and a submission against an `ARMED` session is refused with
`CONFLICT: Session is not locked`, so no unlock token could ever be minted. The
user saw *"Something went wrong / Missing bearer token / Try again"* over a
full-screen overlay, with only the ten-second kill switch as an exit, which
records a failure against them for something that was never their fault.

Three causes, all now closed:

1. **The shell never told the server.** Every path that takes the screen now
   confirms `LOCKED` with the API first (`apps/desktop/src/server-lock.ts`),
   refreshing the access token if it has expired — a 60-minute timer outlives a
   15-minute token, so refresh is the normal case here, not an edge case. On
   failure the screen is **not** taken; the timer stays armed and retries. A
   lock nobody can open is worse than a lock that did not fire.
2. **The main process held no session at all.** `session.enc` had never been
   written. `store()` in `renderer/api.ts` shared the session with the shell
   only at the moment of *login*, and this origin's `localStorage` outlives the
   process — so every later launch rendered a signed-in dashboard while the
   shell held nothing, and the lock page had nothing to borrow.
   `shareSessionWithShell()` now reconciles at startup.
3. **The lock page raced its own auth.** `useLockSession` fired before
   `Providers` finished borrowing the session, 401'd, and landed on an error
   state whose "Try again" could only repeat the same unauthenticated request.
   The query is now gated on auth having settled.

**Codex diagnosed only (3), and I reported the fix complete before it was.** I
guarded the deadline timer and the restore path but missed the IPC handler the
dashboard actually calls, and the user's screen locked a second time. Audit
every caller before claiming a path is closed — there are six, all visible via
`grep -n "engageLock\|takeScreenFor" apps/desktop/src/main.ts`.

**The durable fix is server-side.** `engageDueSessions()` in
`services/lockSessions.ts`, swept every 15s from `index.ts`: the API owns the
deadline and nothing depends on a client being awake. Verified with the desktop
app at **0 processes** — `fireAt 18:53:38.339 → LOCKED at 18:53:41.636`.
`engageLock` was also made atomic (`claimDueSession`) so the sweep and a client
cannot each assign a different problem to the same session.

## The speed gate was a coin flip

The project's own reference solution measured **170 ms** against a **175 ms**
gate, samples spanning 150–190. Identical code was rejected once and accepted
three times. The seeded `bestKnownMs` came from faster hardware than this judge.

`npx tsx scripts/calibrate.ts --write` fixed it across all problems. After:
110/110/100/110 ms against a 189 ms gate, accepted every time.

**Re-run calibration after any judge, hardware or language-version change.** An
uncalibrated gate is not a slightly wrong number; it is a lockout.

## Running it daily

- **Opening the app starts everything.** `ensureBackend` probes `/healthz` and,
  only if nothing answers *and* a command is configured, launches it detached.
  Empty by default, with no env-var override — a command run at startup should
  be one the user wrote into their own config.
- `backendCommand` is `schtasks.exe /run /tn "CodeLock Backend"`. **Do not
  change it back to spawning PowerShell directly**: detached with
  `stdio: 'ignore'` the script gets a crippled environment and the Docker wait
  loop hangs. Task Scheduler owns the process properly.
- `serve-local.ps1` starts Docker Desktop if the daemon is unreachable (checks
  the per-user `%LOCALAPPDATA%\Programs\DockerDesktop` *and* Program Files),
  creates the `codelock-pg` container if missing, and writes
  `%LOCALAPPDATA%\CodeLock\logs\backend-status.json` so the app can say *why*
  rather than just "api down".
- Docker cannot be removed. Postgres could move to a native install, but the
  judge sandboxes every submission in a throwaway container — that container is
  the security boundary for running untrusted code.

**Verified cold start:** all services down, app at 0 processes → open only the
app → `4000/3000/2358` listening, `api ok=True db=up`.

## New, unfinished, and owed

**`autoRearm`** (`TimerConfig`, defaults **off**). Only a *solved* release
re-arms — never the kill switch, or holding Escape buys ten seconds before the
next countdown and the escape hatch becomes a trap. The active-hours window
still applies. **Owed:** a Settings toggle; it is API-only today.

**`popularity`** on `Problem`, plus `weightedPick` — random but biased. The `+1`
floor keeps newly authored problems reachable; `sqrt` stops one famous problem
swamping its tier. `npm run popularity -w @codelock/api` pulls like counts
(dry-run by default) and takes ranking only, never statements.

**Case studies.** `renderCaseStudy` writes Problem/Solution/Results Markdown to
`case-studies/<slug>.md` beside each mirrored solution, linking to the original
problem rather than reproducing it, and committed separately so a prose failure
never costs the user the code they earned. `secondsLocked` is passed as `null` —
it is not carried on the submission, and the line is omitted rather than guessed.

## Two impossibilities, so they are not rediscovered

**Writing to LeetCode.** There is no public write API. Solving in CodeLock
cannot mark anything solved there; anything that appears to is driving a scraped
authenticated session. The read direction works and is already built.

**Importing LeetCode statements.** They are copyrighted, and an MIT licence on a
"leetcode solutions" repository covers that author's code, not the statement.
The canonical *lists* — which patterns, in what order — are facts and are free
to use. Author fresh, or use a licence-cleared corpus.
